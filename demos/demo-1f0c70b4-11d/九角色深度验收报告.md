# 九类角色深度验收与修复记录

验收日期：2026-11-11。范围：管理端17个模块、宠主端，以及同一浏览器内多窗口共享业务数据。使用隔离的 Edge / Playwright 测试环境，不清空或改写用户日常浏览器里的业务库。

## 角色与完整流程

| 视角/角色 | 验证流程和重点 |
|---|---|
| 系统开发者 | 模块接口、事务失败回滚、重复与并发请求、数据一致性、原始数据保留、增量升级幂等及自定义权限/账号绑定保护 |
| 系统测试者 | 全模块/页签导航、可见按钮绑定与布局、真实业务按钮提交、必填与异常状态、异步弹窗、桌面及移动端回归 |
| 系统运维者 | 直接打开离线页面、角色切换/停用、配置与审计、备份导出和校验、损坏备份拒绝、恢复后刷新与持久化 |
| 院长 | 经营报表与日结、办公审批、请假与排班、任务分配、科室与大额报销审批、配置及备份 |
| 前台接待 | 新建客户→宠物建档→会员开卡与充值→接收宠主预约→签到建病历和队列→叫号/入诊；服务权益及保险材料整理 |
| 医生 | 接诊→病历/体征/SOAP→处方与收费/库存→检验采样/检测/审核→影像报告→住院与护理医嘱→知情文书→核对出院；另验专科、复诊、问诊与免疫计划 |
| 财务 | 预交金收取→抵扣→收费补差→出院退余额；员工报销财务复核→院长大额审批→付款/冲正；保险核定、赔付与医疗收入分离 |
| 护理药房 | 读取医生医嘱→执行/记录监护→配药核对→发药→库存批次与调拨往返；禁止开医嘱、取消医嘱和出院决策 |
| 宠物主人 | 登录/建档→选择宠物/医生/时段预约→报告与病历查询→文书阅读和本人签署→账单/权益/会员服务→问诊/消息→保险报销查询 |

“系统开发者、系统测试者、系统运维者”是验收视角，不额外增加产品登录账号。当前产品提供五种员工演示身份和宠主入口。

## 本轮修复和使用优化

1. **演示账号与岗位对齐。** 院长对应店长，护理对应助理/护士；缺少前台、财务员工时补充虚构岗位员工。只迁移仍保持出厂绑定的默认账号，保留用户自定义绑定及权限。
2. **补齐岗位交接断点。** 前台可办理会员及整理保险材料；财务可进入医疗报销核验和赔付登记；护理可办理库存与门店调拨；医生可确认健康计划执行。
3. **拆分临床决策和护理执行。** 护理可记录监护及配发药，医嘱、专科病历、处方模板、医疗文书、取消医嘱和出院决策交由医生。API和按钮同时限制。
4. **补齐员工办公自助。** 各员工可发起本人申请/费用报销、登记本人考勤、更新本人任务。排班、跨员工任务分配、公告/制度维护和办公审批由院长处理。
5. **报销按环节处理。** 财务只处理财务复核和付款，不替代科室/院长审批；财务本人报销须交院长复核、付款。普通员工不能审批或付款。院长账号保留全流程演示能力。
6. **操作人和已读归属明确。** 护理等操作表单默认当前员工，限制代填其他员工；费用和办公流转记录使用实际演示账号；公告已读分别记录，避免一人阅读后全员显示已读。
7. **收起不相关配置。** 非管理员系统页保留岗位相关工作台；护理经营页只显示调拨，减少与记账/经营分析混在一起的操作。无权限按钮提前禁用并提示负责岗位。
8. **修复旧客户弹窗回弹。** 客户详情入口使用后清除一次性参数，离开模块时关闭旧详情并使未完成的异步请求失效，避免新建宠物后重复弹窗遮挡预约。
9. **保留前次预约稳定交互。** 日期、医生、宠物及时段选择保持局部更新；再次覆盖异步乱序、失败重试、提交、取消及窄屏操作。

## 验收证据

最终结果由同版本测试报告记录，交付工具会核对报告中的应用 SHA256 与实际源码，避免拿旧版结果作为新版验收依据。

- `tests/role-boundaries.cjs`：四类员工的本人申请/考勤/报销、财务本人报销回避、前台建计划后由医生按库存批次执行，共6项边界验证。
- `tests/role-journeys.cjs`：五种员工窗口和一个宠主窗口共享隔离数据库，验证跨角色业务交接、岗位限制、本人任务和公告隔离、备份恢复以及角色升级保护。
- `tools/run_recheck.py`：26套原有完整回归，覆盖临床、财务、库存、会员权益、双报销、OA、运营、系统与所有导航页签。
- `tests/alignment-depth.cjs`：临床、经营、移动端、系统四组专业功能验证。
- `tests/data-cycle-closure.cjs`：13组新库/旧库/手工改动保护与两端数据闭环。
- `tests/portal-appointment-interaction.cjs`：6组预约稳定交互验证。
- `tests/check_preservation.py`：原始33张表全部行、字段及原种子数据保持一致；升级写入浏览器增量库。
- `tools/verify_delivery.py`：交付目录与ZIP内容逐字节一致；交付目录和ZIP解压目录分别直接打开冒烟检查。

导航报告里的“按钮样本”用于检查事件绑定和可操作布局；有副作用的业务动作由专项流程提交、核对数据。它不表示每个按钮在所有可能数据状态下都穷举验证。

## 本版本最终结果

- 九类角色验收：18项跨角色流程检查和6项岗位边界检查全部通过；五类员工共55次模块访问通过。
- 完整回归：26/26套通过；专业功能4/4组通过。
- 两端数据闭环及旧库升级：13/13组通过；预约稳定交互6/6组通过。
- 管理端17模块、64页签，192组布局样本、1192个可见按钮/标签样本；未绑定候选、页面脚本错误、导航失败均为0。
- 当前默认演示库：81/81项一致性规则通过，异常0；跨角色交接和恢复后另行检查同样为0异常。
- 原始33张表逐行逐字段保留。交付目录与ZIP解压版将在打包后分别验证，最终机器记录见开发目录 `tests/deep-results/delivery-verification.json`。

其中专业临床回归有一次旧断言只接受原权限提示文案；更新断言兼容新的集中权限提示后，仅重跑该组并合并同源码哈希的结果。拒绝越权的实际行为保持通过；历史失败保存在机器报告 `prior_failures` 中。

## 使用与边界

从“接待与系统”上方切换演示身份。员工按自己的岗位操作；院长可处理管理事项并展示全流程。用同一浏览器打开管理端和 `client/index.html`，可以演示即时数据交接。首次升级前已备份静态交付ZIP；浏览器中自己的业务数据仍应由院长到“备份与恢复”另行导出。

本版仍是本地纯前端演示。角色切换不等于真实身份认证，保险审核/赔付、微信支付、设备回传、云签及消息发送均保留模拟边界。跨电脑、跨浏览器、真实微信与保险联调需要服务端和实际账号，本次验收不宣称这些生产集成已通过。
